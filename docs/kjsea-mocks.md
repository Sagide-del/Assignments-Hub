# KJSEA Mock Test

The student KCSE Papers navigation and dashboard link now open `/student/kjsea-mock-test`. The old `/student/kcse-papers` URL redirects there. Actual historical KCSE assignments, staff authoring options, qualifications and reports are retained; their data is not renamed or deleted.

## Subjects and content

The selector supports all available junior-school subject pools, rather than a hard-coded subject list:

- Original Mathematics generator: 40 multiple-choice questions per paper, covering 32 original practice topics across five practice areas. Exactly 20 questions use a diagram or table. Every template appears once; four visual and four nonvisual templates are repeated with different values. A seed makes a stored snapshot reproducible; new papers randomise values, order and option order. Topic templates and individual items can recur. These are cumulative junior-school revision items for Grade 9 preparation, not a verified transcription of the current KICD subject design or an official KNEC paper.
- Approved question-bank pools: every subject with eligible global PLATFORM questions for Grades 7–9 appears automatically. Canonical grade labels and common numeric/spacing variants are recognised. Only APPROVED multiple-choice items with four distinct options, one matching answer, and a nonempty explanation are eligible. No school-private, generated/unapproved, or senior-school items are selected. Existing learner access to approved global content follows the Learning Coach precedent; trial learners remain blocked by the independent-trial guard.
- Bank papers sample at most 40 unique items, balancing available topics and preferring items not used in that learner’s three recent papers of the same subject. If the pool is smaller, the UI explicitly presents a shorter practice set. Written/practical-response questions are not fabricated or automatically converted into MCQs. Additional subjects need reviewed eligible content, not a frontend code change.
- A bank item’s text, safe rich content, diagram reference, options, key and explanation are snapshotted together. Its option order is shuffled while preserving the correct answer. Existing original bank point weights do not apply: every mock question earns one mark, as disclosed in the interface.
- The “How this paper is built” note distinguishes generated mathematics from bank-backed subjects. Exact topic/visual coverage is computed from the saved paper. The 32-topic/50%-visual maths statement is not applied to other subjects. Platform approval does not imply KICD or KNEC endorsement.

## Student workflow

Choose a subject and untimed practice or a 30/60/90-minute practice limit. Timing starts when the paper is generated and continues when the page is closed. The learner can navigate questions, flag questions for the current session, autosave choices, resume a draft, confirm submission and review explanations, topic priorities and a downloadable text review. The question navigator starts collapsed on small screens. Figures have text alternatives; tables have headers and captions.

Attempts and answers are stored on the server in `kjsea_mock_attempts`, scoped by school and student. A browser backup of answer choices, keyed by learner ID and attempt ID, supports recovery from failed autosaves. It contains the learner’s choices, not an answer key. Save/submission failures are explicit and retryable. Submitted papers use the server answers even if an old browser backup exists. Fresh server state is fetched before mounting a cached paper, so reopening does not restart a timed paper. Flags are session-only and labelled as such.

The service omits keys, explanations and generator seeds from draft responses. It grades the stored snapshot on submission, exposes explanations only after submission and makes repeat submissions idempotent. After the server deadline, new choices are ignored and the last saved server answers are graded. Draft writes cannot overwrite a submitted paper. All per-attempt reads/writes/deletions include both learner and school scope. Completed papers cannot be discarded; unfinished-paper deletion requires a product confirmation. Lists show the latest 30 records. Up to five unfinished papers are allowed; old timed drafts can be opened to finalise or discarded.

## API and deployment

- `GET /kjsea/blueprint`: public maths blueprint and a fixed-ID database-table readiness probe; contains no learner data or keys.
- `GET /kjsea/subjects`: student-only subject/pool metadata.
- `POST /kjsea/attempts`: create a GENERATED Mathematics or BANK subject snapshot; optional practice time limit.
- `GET /kjsea/attempts`, `GET/PATCH/DELETE /kjsea/attempts/:id`, `POST /kjsea/attempts/:id/submit`: student-owned history, answers, draft deletion and marking.

The additive Prisma migration creates the private attempt table and foreign keys; no existing assignments are migrated. Its SQL was generated by Prisma’s schema diff. Render’s configured build runs `prisma migrate deploy` before serving the new backend. The existing GitHub AWS workflow tests and builds the frontend and the mock backend before publishing frontend assets. Before publishing, the workflow polls the live `/api/v1/kjsea/blueprint` route, which probes the new table. If readiness fails, the frontend is not published. The same endpoint is checked after deployment.

## Validation

Backend tests cover 200 generated papers, item uniqueness, all 32 topics/five areas/20 visuals, numeric correctness for diagram/table data, source/subject eligibility, topic balancing, recent-use rotation, honest short sets, option-key preservation, answer hiding, ownership, deadline enforcement, idempotent marking and request validation. Existing assignment scoping tests still pass.

Browser checks with API fixtures cover the old-route redirect and navigation replacement, multi-subject selection, English bank generation, all maths diagrams/tables, autosave failure and browser-backup recovery, refresh, server marking, submission retry, reviewed answers, history, export, discard confirmation, timer expiry and 320/390px layouts. They do not create or alter a real student’s production attempts. Production schema readiness and published assets are verified separately after deployment; authenticated live learner persistence still requires a real learner session.
